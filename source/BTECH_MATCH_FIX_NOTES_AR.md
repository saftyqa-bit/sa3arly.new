# إصلاح مطابقة عروض B.TECH المتكررة — v0.4.3

## سبب فشل المهمة التجريبية الثانية

وصل الـWorker إلى صفحة Fresh FWS400ND الصحيحة، واستخرج الصفحة والسعر، لكن الصفحة
قدمت العرض نفسه عبر أكثر من مصدر منظم مثل HTML وJSON-LD. كان محرك المطابقة
يعامل النسختين المتقاربتين جدًا كعرضين مختلفين، ولذلك أعاد
`product_match_failed` رغم أن كلاهما يشير إلى الرابط والسعر نفسيهما.

## ما تغيّر

- يحتفظ النظام بإصلاح Browser Fallback الموجود في `v0.4.2`.
- يعتبر عنوانين متقاربين دليلين لنفس العرض فقط عندما يتطابق الرابط والسعر.
- يرفض الدمج إذا اختلف GTIN أو SKU أو السعر أو الرابط.
- يفحص جميع البدائل داخل هامش الالتباس؛ وجود بديل مختلف فعليًا يظل مانعًا للنشر.
- لا يغيّر API أو PostgreSQL أو عدد المهام أو جدولة التحديث كل 12 ساعة.

## نتيجة الاختبارات المحلية

- جميع الاختبارات: `60/60` ناجحة.
- Ruff: لا أخطاء.
- عرض Fresh FWS400ND يطابق Variant المستهدف بدرجة `83.873`، أعلى من حد صفحات
  المنتجات المباشرة `40`، ولم يعد الدليل المكرر يسبب رفضًا كاذبًا.
- اختلاف الرابط أو السعر داخل هامش الالتباس يظل مرفوضًا في اختبارات الانحدار.

## سلوك سكربت النشر

`DEPLOY_BTECH_MATCH_FIX_WORKER.sh` يبني Worker جديدة بلا ترافيك، يفحصها بطلب آمن لا
ينفذ مهمة، ثم يحول الترافيك إليها مع إبقاء Cloud Tasks في حالة `PAUSED`. لا
ينشئ Scheduler ولا يشغّل أي مهمة. عند أي خطأ يعيد Worker السابقة ويعيد إيقاف
الطابور.
